# Repository Guidelines

This quick-reference distills the detailed guidance under `.github/instructions` so agents and contributors can stay aligned without re-reading every file. When unsure, open the linked instruction for full context.

## Architecture & Modules
- AniTrend v2 follows a strict domain/data/presentation split: domain hosts pure Kotlin use cases and repository contracts, data implements them via support-arch `DataState`/`UiState`, and feature or common modules deliver UI and ViewModels (see [.github/instructions/context.instructions.md](.github/instructions/context.instructions.md)).
- Module paths are centralized in `buildSrc/module/Modules.kt`; keep new modules registered there so the CorePlugin can wire plugins, dependencies, and Koin bindings automatically (see [.github/instructions/build-system.instructions.md](.github/instructions/build-system.instructions.md)).
- Koin modules live beside their features or data sources. Always expose new implementations through the local `Modules.kt` loader and include them from the relevant app/core aggregator to ensure DI graph completeness (see `.github/instructions/context.instructions.md`).

## Build System & Tooling
- Dependency versions live in `gradle/libs.versions.toml`. Update the catalog and use the generated `libs.*` accessors instead of hardcoding artifacts (see `.github/instructions/build-system.instructions.md`).
- Gradle convention logic resides in `buildSrc`. The CorePlugin applies Android/Kotlin plugins, configures compile options, injects secrets, and attaches shared dependencies—keep module build files minimal and rely on these conventions.
- Common tasks: `./gradlew assembleDebug`, `./gradlew test`, `./gradlew connectedDebugAndroidTest`, `./gradlew lint`, and `./gradlew spotlessCheck|spotlessApply`. Run Spotless before committing to satisfy formatting checks.
- The project ships multiple flavors (e.g., `google` vs OSS). Ensure new logic respects flavor-specific behavior, especially around Firebase integrations.

## Coding Style & Naming
- Kotlin/XML formatting is enforced via Spotless + ktlint (.editorconfig sets 4-space indents and 150-char width). Avoid manual style tweaks—run Spotless instead.
- Place business logic in domain `*UseCase`/`*Interactor` classes; repository interfaces keep the `I` prefix with concrete implementations in `:data`. Compose functions may break casing rules only when annotated with `@Composable`.
- Use semantic resource prefixes (`label_`, `title_`, `placeholder_`, `action_`, etc.) to keep string assets predictable (see `.github/instructions/guides.instructions.md`).
- Install Git hooks (`./.githooks/setup.sh`) to enforce `<type>/<description>` branch names.

## Data & Persistence
- Follow the Room join-table checklist: nullable autogenerated surrogate IDs, composite unique indices, upsert by logical keys, and mapper-based batch inserts. Always validate migrations and export schemas under `data/schemas` (see [.github/instructions/data.guides.instructions.md](.github/instructions/data.guides.instructions.md)).
- When introducing new storage, pair entities, DAOs, and repositories with the existing mapper + DataState patterns so paging, caching, and refresh flows remain consistent.
- In `data/edge`, keep remote models concrete and schema-faithful. Prefer adapting edge payloads in converters, mappers, entities, and entity views instead of adding compatibility hacks, implicit JSON container types, or shape-derivation logic directly to serialized models.

## Testing Expectations
- Mirror production package names for tests. Lean on JUnit4, MockK, Turbine, and `kotlinx-coroutines-test` to exercise asynchronous flows coming from `DataState`.
- Compose or Espresso UI paths belong in `androidTest`; call out device/emulator requirements in PR notes.
- Always run `./gradlew test` plus any impacted instrumentation suites before submission and include the results in the PR checklist.

## Commit & PR Workflow
- Follow Conventional Commits (`feat:`, `fix(data):`, `refactor(app):`, etc.) and rebase onto `develop` before pushing.
- Verify lint, Spotless, and schema exports locally; mention affected modules, behavioral notes, and attach screenshots/GIFs for UI changes.
- Flag migrations, configuration toggles, or secret-handling updates explicitly so reviewers can focus on high-risk areas.

## Key Libraries & Integrations
- Networking uses Retrofit + OkHttp with AniTrend’s GraphQL converter alongside Kotlinx Serialization. Reuse the shared clients provided through Koin rather than instantiating ad hoc clients.
- Coil (with SVG/GIF/video support), Chucker for debug HTTP inspection, android-emojify, support-markdown (Markwon), and Material3 Compose are preconfigured via shared modules—tap into those bindings instead of creating new singletons (see `.github/instructions/project-scope.instructions.md`).
- WorkManager-backed jobs reside in `:task/*`; Android platform utilities live under `:android/*`. Keep cross-module dependencies flowing from domain → data → app/feature to preserve the clean architecture boundaries.

## Configuration & Security
- Secrets stay outside VCS in `.config/*.properties` or `local.properties`. BuildSrc injects them into `BuildConfig`; never commit credentials or service JSON.
- Review `SECURITY.md` and monitor `./gradlew --warning-mode all` for dependency/configuration alerts.
- Coordinate any schema or API shifts with the AniTrend edge/back-end owners before merging, especially when touching `:data:edge` modules.

## Working With AI Assistants
- Include module name, layer (domain/data/feature), and desired DataState/UiState behavior in prompts so generated code follows existing conventions.
- Reference the instruction files directly in prompts when seeking architectural or build guidance; they capture the authoritative patterns summarized above.
